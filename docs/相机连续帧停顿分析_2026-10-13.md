## 造成帧间停顿的候选路径

### 1. SDK 计算路径阻塞（优先验证）

两次有效配置均为 HD720、采集 30 FPS、发布 15 Hz、NEURAL LIGHT 深度、depth_stabilization=30、pos_tracking_enabled=true、async_image_retrieval=false。YOLO 与 ZED 同时使用 GPU。

当前本机驱动在 zed_camera_component_main.cpp:4196 附近检查/启动位置跟踪，在 :4281 调用 grab(mRunParams)，成功后才走 processVideoDepth。图像不是绕过 SDK 深度和跟踪计算的独立 USB 转发流。common_stereo.yaml:71 明确指出 depth_stabilization>0 会强制启动位置跟踪；仅关闭 TF 发布没有取消这部分计算。其额外计算开销也见 Stereolabs 官方 stereo node 文档。

当前感知覆盖配置 zed_hardware.yaml 没有覆盖 depth_stabilization，继承默认 30，并显式开启位置跟踪。这是值得做减负对照的配置点，但没有 GPU/SDK处理耗时数据，不能把它写成已确认故障根因。

### 2. 图像/深度发布线程阻塞或丢帧（优先验证）

驱动 videoDepth.cpp:2340 的线程取得 mVdMutex，调用 handleVideoDepthPublishing；后者发布图像/深度并控制发布频率。采集侧 processVideoDepth (:1286 附近) 对同一锁 try_lock，失败则跳过本次图像/深度提取。如果发布耗时增加，后续采集结果可能无法交接。

ZED mQos 为默认 QoS(depth=10)，图像/深度可跨进程传给 Python 检测、C++立体适配器和自检节点。1280×720 的四通道 uint8 图像约 3.69 MB/帧，15 Hz 约 55.3 MB/s；float32 深度大小相当，二者逻辑载荷合计约 110.6 MB/s，尚未计入拷贝和其他订阅。该数值是源码格式对应的估算，不是本次带宽实测。应检查发布耗时与进程间接收延迟，不宜直接认定 USB 带宽不足或 QoS 不兼容。

### 3. 检测处理与原始帧到达脱节（应同时区分）

YOLO 当前 on_image 只覆盖 latest，独立工作线程负责推理与标注；所以模型推理慢可以导致检测结果/标注图更新慢，而原始相机帧仍到达。不能只靠观察下一张处理后的画面判断原始数据断联。现有 status 话题包含 inference_ms、cycle_ms 和源 stamp_ns，但本次运行没有将这些消息保存为时序日志。

## 检查逻辑缺口与改进

start_full_fsd.sh:529 使用 ros2 topic echo --once --field header；只验证一条完整 Image 到达。--field header 是收到完整消息后取字段，并不减少 DDS 图像载荷。20 秒包括 CLI 启动、DDS发现、相机初始化和首帧传输。

mission_manager.cpp:132–136 的相机回调忽略 msg，只把 camera_last_seen 设为 now()。因此持续收到旧时间戳图像仍可通过自检，且只要间隔小于 sensor_timeout_sec=2 就不会判故障，即使 15 Hz 图像变成每秒一帧。

建议按以下顺序定位与改进，尚未修改运行配置：

1. 在同一时段同步记录：ZED diagnostics 的 grab频率/处理耗时、Video/Depth频率/发布耗时、Frame Drop rate；原始图像接收时间、header stamp、帧间隔、源图像年龄；YOLO status 的推理/周期耗时；GPU利用率与显存。用到达时间的单调时钟测间隔，源图像年龄使用与 header 对应的 ROS/系统时钟并监测时钟跳变。
2. 首帧后继续观察 5 秒，以 Depth=1 的轻量订阅采样连续帧，报告接收频率、最大间隔、时间戳重复数、P95源图像年龄。作为独立“帧流质量”结果，避免把首次收到任意旧帧当作整条相机链路通过。
3. 若 grab频率下降或SDK处理耗时变长：先单独停用 YOLO 做对照，再以 pos_tracking_enabled=false 和 depth_stabilization=0 成对做对照，保留立体深度输入。关闭稳定化会改变深度噪声，应验证锥桶测距质量。不要只关闭位置跟踪，因为稳定化会重新要求它。
4. 若 grab正常而发布频率低/发布耗时高：查发布线程、DDS大消息资源和订阅端；如果发布正常但接收端年龄/间隔异常，再查传输和接收调度。只有这些数据才足以区分采集、发布、传输与检测停顿。
5. 不直接延长全部超时，不把 async_image_retrieval=true 当作无验证的修复；其开启需检验 RGB/深度同步，当前立体适配器依赖对应时刻的深度。
