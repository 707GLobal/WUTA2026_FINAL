## 启动路径

实际入口为start_fsd_manager.sh → fsd_startup/manager.py → start_full_fsd.sh。直接运行根脚本时，tools/run_logged.py负责日志生命周期。CLI在提交根脚本前执行权限处理、并行预检查，并设置FSD_PARALLEL_CHECKS=1。

最新样本的近似阶段时间（manager.log显示到秒）：

| 阶段 | 时间 |
| --- | --- |
| 创建运行、sudo认证、并行预检查 | 12:24:38，预检查约0.19 s |
| 环境加载、CAN初始化 | 12:24:39～40 |
| 惯导、静态TF、感知驱动及算法启动 | 12:24:40～42 |

| 任务广播通过、提交RViz、宣告完成 | 12:24:59 |

可优化点：

1. **定位与相机初始化重叠。** 根脚本762～781行等待相机/雷达/惯导及融合输出之后才启动EKF和定位管理。EKF实际依赖惯导输入，没有必要等待相机模型初始化。可提前启动现有定位节点并并行观察定位首帧，保留控制与任务门控；最终收益须实测。
2. **固定逐组等待。** start_group每次sleep 0.3，正常全车样本启动15组，累计显式等待4.5 s。应按依赖分批启动并统一检查存活/就绪，不能直接把4.5 s全部视为可节省时间，因为驱动初始化已在后台重叠执行。
3. **重复创建话题检查进程。** 雷达、图像、惯导已并行，但融合、pose、任务广播仍逐阶段启动ros2 topic echo。显式消息类型已配置，不是等待类型发现的问题；进程启动、DDS匹配仍有成本。宜在既有检查机制中共享一次ROS上下文、并行订阅所需首帧，保留各项独立结果和超时。
4. **观察器等待位于驾驶节点之前。** mission_review就绪文件最多等待3 s；本样本约1 s。它是只读记录，可考虑提前与其他初始化重叠，避免简单后移导致早期采集缺失。
5. **入口行为不同。** CLI已启用传感器并行检查，根脚本默认FSD_PARALLEL_CHECKS=0。把“开启并行检查”作为CLI的新优化不会产生该项收益；可统一两种入口默认行为。
6. **重复环境与配置解析为次级项。** 根脚本加载多个setup.bash；华测和显示入口又加载环境。华测用11次独立Python读取同一YAML，ZLG也逐项读取。可一次解析并保持现有覆盖优先级；不应先假定这是主要瓶颈。

本批成功样本没有强制构建参数；最新日志也无构建步骤。根脚本默认auto仅在安装入口缺失时构建，不能将此次慢启动主要归因于colcon。ZLG入口每次make会检查依赖，但无改动不等于每次完整重编译。

## 停止路径与首要疑点

根脚本cleanup先发送SIGINT，再以20×0.5 s轮询已登记的顶层PID；仍未结束时发送SIGTERM并逐个wait。它没有最终SIGKILL和wait上限。CLI先等待根脚本最多12 s，之后processes.cleanup对残留执行INT/5 s、TERM/2 s、KILL/1 s。后者是兜底，不是每次固定额外等待8 s；权限失败时逐PID提权发送信号还会额外耗时。

最新样本中：

- controller首次记录停止信号：12:25:19.511837。
- ZED关闭开始：12:25:19.638685；区域地图保存成功：12:25:20.032568。
- CAN桥在12:25:20、22、24、26、28仍持续记录VCU接收计数，直到12:25:29.820附近进入退出收尾，12:25:30.507记录“已退出”。
- manager完成清理和归档：约12:25:30.552。

这高度指向**第一轮CAN桥停止信号未生效，耗尽根脚本约10秒宽限期后才退出**。根脚本对ZLG只向sudo PID发送SIGINT，依赖sudo → tools/run_privileged_group.py → 独立桥进程组转发；其余组直接接收组信号。现有日志未记录每层信号到达，尚不能确定是sudo转发、信号继承还是其他环节，不能直接断言sudo是已证实根因。

建议先在现有监管器中记录单调时间、目标PID/PGID、信号转发及子进程退出，再用无硬件进程复现真实sudo启动链，确认第一轮信号能到桥。ZLG的C程序已为INT/TERM注册相同的正常退出处理，可评估监管链采用适合的可转发停止信号；不必先缩短所有节点的退出时间。

退出判定也需改进：当前根脚本只检查顶层PID，不能充分证明整个所属进程组结束；TERM后无界wait会造成独立根脚本卡住。应复用现有PID启动时间身份检查，对所属进程/组建立统一、有界的停止预算，CLI继续负责崩溃残留兜底，避免重新发起完整宽限周期。台架已有0.7 s中性释放等待必须保留其语义。

启动过程中停止还存在潜在延迟：UI的stop/quit排在当前检查操作之后；根脚本部分前台命令会延后处理trap，并行话题探针也没有登记进CHILD_PIDS。应让现有检查支持取消并登记、回收探针。本批日志不能量化按键排队时间。

## 驱动配置与退出异常

- 源码zed_hardware.yaml仍设置pos_tracking_enabled=true，而权威车辆定位来自EKF/定位管理。实际日志确认ZED启动位置跟踪、加载area memory并在退出保存。可在核实深度稳定化、显示及其他消费者依赖后，评估关闭不需要的位置跟踪/区域记忆。最新样本保存仅约0.39 s，不是约11 s停止的主要解释。
- 最新停止日志中rslidar_sdk_node因std::system_error/Invalid argument以-6退出，华测HcCgiProtocolProcessNode以-11退出。应单独排查驱动析构和重复信号路径；目前不能将它们判定为10秒等待的直接原因。
- 保持驱动跨运行常驻虽可减少冷启动，但当前任务状态、地图、定位原点和记录会话没有统一reset协议，不建议作为第一轮优化。

## 实施优先级与验证

| 顺序 | 工作 | 收益判断 |
| --- | --- | --- |
| 1 | 修复/验证CAN监管链首轮停止；为每组记录停止耗时；有界退出 | 最明确，目标消除当前反复出现的约10秒等待；剩余耗时实测 |
| 2 | 提前启动定位、按依赖分批启动、检查共享ROS上下文 | 启动有数秒级优化空间，收益不能简单相加 |
| 3 | 检查取消与探针回收 | 改善启动失败或启动中按停止的响应 |
| 4 | 评估ZED位置跟踪、合并重复YAML读取和环境加载 | 次级优化，先保留必需相机/深度功能 |

先用模拟进程验证INT/TERM转发、忽略信号的超时升级、组长先退/子进程残留、取消首帧检查、外部复用进程保护及日志最后写入完成。再在受控实机分别采集冷启动与再次启动数据，按现有正常/台架/人工记录模式验证停止顺序。不得以减少检查、绕过真实首帧、GNSS/GO门控或提前宣告就绪作为性能改善。
